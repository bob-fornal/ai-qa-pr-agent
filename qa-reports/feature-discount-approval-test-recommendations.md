This branch adds manager approval for discounts above a threshold (behind a feature flag), but also rewrites all pricing to integer cents, adds a data migration, an admin CSV export, a manager webhook, and moves the runtime from Node 18 to Node 22, with almost no tests for the new behavior and the regression test for the claimed tax-rounding fix skipped. The biggest risk is around who can approve discounts and what the customer is actually charged: the review endpoint uses a deny-list (`user.role === 'sales'`), there is no self-approval guard, checkout is allowed while a discount is pending, and a discount can be approved after the order is paid. Test the approval authorization and the approval-to-checkout money flow first.

## Critical Path Details

### CP-1: Who can approve/reject a discount (P0, Impact 5 × Likelihood 5 = 25)

- **Entry point(s):** `POST /api/orders/:id/discount/review`; Approve/Reject buttons in `public/index.html` / `public/app.js`
- **What changed:** New route in `sample-app/src/server.js` with a deny-list check (`if (user.role === 'sales') return 403`) instead of the allow-list `hasRole(user, [...])` used by every other discount route; new `reviewDiscount` in `sample-app/src/orders.js`. Any role other than `sales` (including future roles) can approve. No guard against a manager/admin approving a discount they set themselves (managers are allowed to set discounts), and the requester is not recorded, only `approvedBy`.
- **Why it's critical:** This control decides who can give away money. A wrong check means unauthorized discount approvals, broken separation of duties, and an incomplete audit trail.
- **Existing coverage:** None. `test/auth.test.js` covers `hasRole` only; `test/orders-api.test.js` has no review tests.
- **Preconditions / test data:** Users `sam` (sales), `maria` (manager), `ada` (admin); `FEATURE_DISCOUNT_APPROVAL=true`; an open order with a pending discount > 15%.

**Automated** (integration): A role matrix is combinatorial, and the deny-list is easy to regress.
- Given a pending discount, when `sam` posts a review, then 403 and `approvalStatus` stays `pending`.
- When `maria` or `ada` approves, then 200, `approvalStatus=approved`, `approvedBy` = that user.
- No token gives 401; a tampered token gives 401.
- Given a verified token whose role is not in {manager, admin}, then 403. This documents the deny-list gap and fails today.
- (Once decided, see Open Questions) Given `maria` set the 30% discount, when `maria` approves it, then 403.

**Smoke** (staging, prod): A rollback decision depends on authorization working in each environment.
- `sam` calling review on any order returns 403.

**Manual** (exploratory): Abuse cases need judgment.
- Charter: Explore the review endpoint with direct API calls as each role to discover privilege escalation, self-approval, approving non-pending orders, and missing audit data.

**Not recommended:** E2E UI automation. The authorization is server-side and integration tests cover it more reliably.

### CP-2: Large-discount approval workflow through checkout (P0, Impact 5 × Likelihood 5 = 25)

- **Entry point(s):** `POST /api/orders/:id/discount`, `POST /api/orders/:id/discount/review`, `POST /api/orders/:id/checkout`, `GET /api/orders/:id`
- **What changed:** `setDiscount` sets `approvalStatus='pending'` when the flag is on and pct > threshold; `calculateTotal(items, {pct, approved})` zeroes the discount while pending; rejection resets `discountPct` to 0. Observed defects or ambiguities:
  - `checkout` does not block pending orders, so the customer pays full price.
  - `reviewDiscount` does not check `status === 'open'`, so a paid order can be approved afterwards. The order's computed `totalCents` then no longer matches `paidTotalCents`.
  - Legacy orders with pct > threshold and `approvalStatus=null` show `pending_approval` when the flag is turned on, but review returns 409, so they are stuck.
  - Turning the flag off silently applies any pending discount.
- **Why it's critical:** Customers are charged the wrong amount, orders get stuck in states nobody can resolve, and recorded vs. displayed totals disagree.
- **Existing coverage:** One unit test (`large discounts wait for approval when the feature is on`) in `sample-app/test/pricing.test.js`. It mutates global `config` and only resets it if the assertion passes. No API-level workflow tests.
- **Preconditions / test data:** Flag on/off; threshold 15; orders `1001` (open, 0%), `1002` (open, 10%), `1003` (paid); a legacy order with > 15% discount.

**Automated** (unit, integration): These are deterministic state transitions with clear expected outputs.
- Unit: `calculateTotal` matrix over flag on/off × pct 0 / 15 / 15.01 / 30 / 50 × approved true/false. Check `discountCents` and `discountStatus` (`none` / `applied` / `pending_approval`). Restore config even when a test fails.
- Integration: full lifecycle.
  - Set 30% → `pending_approval`, discount 0.
  - Approve → `applied` with the discount deducted.
  - Reject → pct 0, status `none`.
  - Second review → 409; `decision: "maybe"` → 400; unknown order → 404.
- Integration: Given an approved 20% discount, when sales changes it to 40%, then the order returns to pending and `approvedBy` is cleared. When changed to 10%, `approvalStatus` is null.
- Integration: Given a pending discount, when the order is checked out, then pin the expected behavior per the product decision (blocked vs. charged full price). Given a paid order, review is rejected and `paidTotalCents` is unchanged.

**Smoke** (staging, flag on): The core new journey depends on a per-environment flag.
- Sales sets 30% on an open order → banner shows "pending"; manager approves → discount applied.

**Manual** (exploratory + business acceptance): A new feature with ambiguous rules.
- Charter: Explore discount lifecycles across flag states, re-edits, checkout and concurrent manager/sales sessions to discover wrong charges and stuck states.
- Product owner acceptance of the threshold boundary ("above 15", so exactly 15 is auto-applied).

**Not recommended:** Automated E2E. Unit and integration tests cover the logic, and the UI is a thin wrapper.

### CP-3: Order totals & amount charged in integer cents (P0, Impact 5 × Likelihood 5 = 25)

- **Entry point(s):** `GET /api/orders/:id`, `POST /api/orders/:id/checkout`, CSV export
- **What changed:** `sample-app/src/pricing.js` was rewritten to cents (`toCents`, `Math.round(subtotalCents*pct/100)`, `Math.round(taxable*taxRate)`), and `checkout` now stores `paidTotalCents`. The commit claims it "fixes tax rounding drift", which makes it a bug fix, yet the regression test `tax rounds to the nearest cent` was changed to `test.skip` with "TODO: re-enable after the cents migration settles".
- **Why it's critical:** Wrong rounding means wrong charges and tax amounts on every order.
- **Existing coverage:** Partial. Tests cover no discount and 10%; the rounding regression test is skipped (likelihood raised for the skipped test and for money rounding). Fractional `discountPct` (validation allows any finite 0–50), half-cent ties, prices like 10.05 and multi-quantity cases are not covered.
- **Preconditions / test data:** Order `1003` (CAP 10.05 × 3), `TAX_RATE=0.07`, fractional discounts.

**Automated** (unit, integration): A bug fix with deterministic arithmetic needs a regression test.
- Un-skip `tax rounds to the nearest cent`: CAP 10.05 × 3 gives `taxCents=211`. It must fail on the old dollar-based code and pass now.
- Unit boundary cases: half-cent discount and tax ties (confirm the rounding policy), `discountPct` 12.5 and 50, prices whose `price*100` is not exact in floating point, large quantities.
- Unit: `totalCents == subtotalCents - discountCents + taxCents`, and every output is an integer.
- Integration: after checkout, `paidTotalCents` equals the `totalCents` shown before checkout, with and without an approved discount.

**Smoke** (staging, prod): Totals are on the primary transaction.
- `GET /api/orders/1001` returns `totalCents: 4815`; the UI shows "$48.15".

**Manual** (scripted): Verify the original bug fix by reproducing the "rounding drift" scenario. No repro steps were provided (see Open Questions).

**Not recommended:** Performance testing. The computation is trivial.

### CP-4: Migration 002 on existing order data (P0, Impact 5 × Likelihood 4 = 20)

- **Entry point(s):** App startup (`runMigrations` in `sample-app/src/db.js`) against a persisted `DATA_FILE`
- **What changed:** New `sample-app/migrations/002_discount_approval.js`. It sets `approvalStatus`/`approvedBy` to null on all orders, converts `paidTotal` → `Math.round(paidTotal*100)` as `paidTotalCents`, and deletes `paidTotal`. There is no `down` migration, and the previous app version would no longer find `paidTotal`.
- **Why it's critical:** It rewrites recorded payment amounts in place, and rollback is not straightforward.
- **Existing coverage:** None. Tests only use `:memory:`, whose seeds have no `paidTotal`.
- **Preconditions / test data:** A copy of a production-like JSON data file with paid orders that have float `paidTotal` (for example 48.15, 32.27), open orders with > 15% discount, and an already-migrated file.

**Automated** (integration): A data migration against representative data.
- Given a data file with paid orders that have float `paidTotal`, when the app starts, then each `paidTotalCents` is exactly the rounded cents value, `paidTotal` is removed, and `002_discount_approval.js` is recorded in `meta.migrations`.
- Given an already-migrated file, when the app restarts, then nothing changes (idempotent).
- Given a legacy open order at 20% with the flag on, then the expected state is defined. Today it shows `pending_approval` but cannot be reviewed.

**Smoke** (staging, prod): The app must boot against migrated data.
- The service starts, `/health` is OK, and a previously paid order returns `paidTotalCents` with no `paidTotal`.

**Manual** (scripted): A one-time operation.
- In staging, before and after migrating a production-data copy, spot-check paid totals.
- Rehearse rollback: restore the data-file backup and run the previous version.

**Not recommended:** Exploratory. The migration is narrow and deterministic.

### CP-6: Admin CSV export of orders (P1, Impact 4 × Likelihood 3 = 12)

- **Entry point(s):** `GET /api/orders/export`
- **What changed:** New route in `server.js` plus `listOrders` in `orders.js`.
  - Admin-only via `hasRole`.
  - Builds CSV with a plain `join(',')` and no escaping or quoting, so it is open to formula injection via `customerEmail`.
  - Exports customer emails (PII).
  - `totalCents` is recalculated live rather than taken from `paidTotalCents`.
  - The route also matches `/api/orders/export/...`.
- **Why it's critical:** It is a bulk PII export, and the CSV can be corrupted or used for injection in spreadsheet tools.
- **Existing coverage:** None.
- **Preconditions / test data:** Users `ada`, `maria`, `sam`; orders with emails containing commas or quotes, or starting with `=`/`+`.

**Automated** (integration):
- `ada` gets 200, `text/csv` and the exact header row; `maria` and `sam` get 403; no token gets 401.
- Given an email with a comma or a leading `=`, the cell is escaped or neutralized (fails today).
- Paid orders export the amount actually charged (confirm whether that should be `paidTotalCents`).

**Smoke** (staging): `ada` can download the export; `sam` gets 403.

**Manual** (exploratory):
- Open the export in Excel and Google Sheets: check columns, injection and encoding.
- Privacy review of who may export email addresses.

### CP-7: Manager notification webhook (P1, Impact 3 × Likelihood 4 = 12)

- **Entry point(s):** `setDiscount` → `notifyDiscountPending` in `sample-app/src/notifier.js` when approval is needed
- **What changed:** A new outbound integration: POST to `NOTIFIER_WEBHOOK_URL` with a 2-second timeout.
  - The payload includes `customerEmail`.
  - `console.log` writes the customer email (PII in logs).
  - Errors are swallowed and the call is not awaited, so a failed notification means managers are never told about the pending discount, with no retry.
- **Why it's critical:** Silent notification failures stall pending discounts. PII also goes to a third party and to the logs.
- **Existing coverage:** None.
- **Preconditions / test data:** A local stub webhook; variants with no URL, slow (> 2 s), 500, and unreachable.

**Automated** (unit, integration):
- No URL → no request.
- Discount above the threshold → exactly one POST with `type: discount.pending` and the expected fields; at or below the threshold → no POST.
- A slow or failing webhook does not delay or fail the discount API response; the failure is logged and nothing crashes.

**Smoke** (staging): Set a discount that needs approval and confirm the webhook receiver gets the event. This needs real staging credentials.

**Manual** (scripted):
- Confirm the managers' channel receives a readable notification.
- Privacy and logging review of the email in logs and payload.

**Automated** (unit):

**Smoke** (staging, prod): `/health` shows the intended flag value for each environment.

**Not recommended:** Manual. These are binary checks covered by smoke.

## Coverage Gaps & Risks

- **Skipped test:** `tax rounds to the nearest cent` is `test.skip`'d. It is the regression test for the bug this PR says it fixes.
- No API-level tests exist for the review endpoint, export, approval workflow, notifier or migration. All new behavior rests on one pricing unit test.
- `pricing.test.js` changes global `config.features` and only resets it if the assertion passes, so a failure can leak into later tests.
- The repo has no UI/component, contract or migration test layers; only `node:test` unit and in-process API tests.
- **Authorization:** the review endpoint uses a deny-list (`user.role === 'sales'`) instead of `hasRole(user, ['manager','admin'])`.
- **Logic gaps:**
  - No self-approval guard, and the requester is not recorded.
  - `reviewDiscount` doesn't check that the order is open.
  - Checkout is allowed while a discount is pending.
  - Legacy orders above the threshold get stuck when the flag is turned on.
- **Breaking contract:** the order API's dollar fields were removed; external consumers are unknown; the version bump is only minor.
- **PII:** customer email is logged in `notifier.js`, sent to the webhook, and included in the CSV export.
- **Rollback:** migration 002 has no `down` step, so rollback needs a data restore.
- **Intent vs. diff:** the stated intent (approval feature) only partly matches the diff, which also bundles a pricing-model rewrite, a data migration, a CSV export and a runtime upgrade. That gives 10 P0/P1 paths, the limit this process allows. Consider splitting at least the runtime upgrade and the CSV export into separate PRs.
