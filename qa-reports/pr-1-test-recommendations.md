- Flag-gated manager approval for large discounts
- A review endpoint
- A manager webhook

## Critical Path Details

### CP-1: Order pricing and checkout totals in cents (P0, Impact 5 × Likelihood 5 = 25)

- **Entry point(s):** `GET /api/orders/:id`, `POST /api/orders/:id/discount`, `POST /api/orders/:id/checkout`, order screen.
- **What changed:**
  - `sample-app/src/pricing.js`: `calculateTotal` now uses integer cents, takes an options object `{ pct, approved }`, rounds each component with `Math.round`, and returns `discountStatus`.
  - `sample-app/src/orders.js`: `checkout` stores `paidTotalCents` instead of `paidTotal`.
- **Why it's critical:** a rounding or units error mischarges every order. The rounding policy also changed (the discount is rounded before tax), so totals may differ by a cent from the last release. Likelihood was raised for float money math and the skipped test.
- **Existing coverage:**
  - `sample-app/test/pricing.test.js` covers 0% and 10%.
  - "tax rounds to the nearest cent" is now `test.skip` ("TODO: re-enable after the cents migration settles") even though the PR claims a rounding fix.
  - `orders-api.test.js` asserts `totalCents` for order 1001 only. The checkout test doesn't assert `paidTotalCents`.
- **Preconditions / test data:** seed orders 1001, 1002 (10%) and 1003 (paid, 10.05 × 3); `TAX_RATE=0.07`; flag off and on.

**Automated** (unit, integration): the math is deterministic, half-cent boundaries are easy to miss, and the bug-fix claim requires a regression test.
- Re-enable the rounding test: given CAP 10.05 × 3, `taxCents` is 211. Add inputs where the old dollar math drifted, so the test fails without the fix.
- Boundary table: float-unsafe prices (0.1, 0.29, 10.05, 19.99) at several quantities, plus discounts and tax that land on half cents. All outputs are integers, and `totalCents = subtotalCents - discountCents + taxCents`.
- With the flag off, discounts of 0 and 50 give `discountStatus` `none` and `applied`.
- Given order 1002 with 10%, when it's checked out, `paidTotalCents` equals the `totalCents` shown before checkout.

**Smoke** (staging, prod): unit-conversion bugs are obvious right after deploy and would drive a rollback.
- Load order 1001: $45.00 / $3.15 / $48.15.

**Manual** (scripted): the rounding policy change needs business sign-off.
- Finance compares totals for a sample of real orders between the old release and this branch, and accepts any one-cent differences.

### CP-2: Large-discount approval lifecycle (P0, Impact 5 × Likelihood 5 = 25)

- **Entry point(s):** `POST /api/orders/:id/discount`, `POST /api/orders/:id/discount/review`, `POST /api/orders/:id/checkout`, approval banner.
- **What changed:**
  - `setDiscount` sets `approvalStatus: 'pending'` when the flag is on and `discountPct > threshold`, then notifies.
  - New `reviewDiscount` approves (sets `approvedBy`) or rejects (resets `discountPct` to 0).
  - Pricing withholds pending discounts.
- **Why it's critical:** unapproved discounts lose revenue, and lost approvals overcharge customers. Two defects:
  - `checkout` doesn't block pending orders.
  - `reviewDiscount` doesn't check `order.status`, so a paid order can be reviewed, and its recalculated total then diverges from `paidTotalCents`.
- **Existing coverage:** one unit test (pending when the flag is on). No API tests for review, 400/409, or checkout while pending.
- **Preconditions / test data:** `FEATURE_DISCOUNT_APPROVAL=true`, threshold 15; users sam (sales), maria (manager), ada (admin).

**Automated** (unit, integration): a state machine with clear transitions, testable with the existing `node:test` in-memory server.
- Sam sets 30% → `pending_approval` with `discountCents` 0. Maria approves → `approved`, `approvedBy` maria, discount applied. Rejecting instead → `discountPct` 0, `rejected`.
- Boundary: 15% applies immediately; 15.5% goes to pending.
- Review with nothing pending → 409; bad or missing `decision` → 400; unknown order → 404.
- Changing the discount after approval puts it back to pending and clears `approvedBy`.
- Checkout while pending, and review after checkout: pin the intended behavior once it's confirmed (likely 409 for orders that aren't open).

**Smoke** (staging, flag on): confirms the end-to-end wiring in the environment where the flag is enabled.
- Sam sets 30% and sees the banner; maria approves; the total shows the discount.

**Manual** (exploratory): a new feature with complex state and open policy questions.
- Explore with all roles in two sessions: checkout while pending, review after checkout, concurrent reviews, edits between the request and the review, and self-approval.

### CP-3: Authorization to review discounts (P0, Impact 5 × Likelihood 4 = 20)

- **Entry point(s):** `POST /api/orders/:id/discount/review`.
- **What changed:** `sample-app/src/server.js` guards this route with `if (user.role === 'sales')`. That's a deny-list, unlike the `hasRole` allow-list used elsewhere. Any role other than sales, including future roles, can approve. Self-approval isn't prevented.
- **Why it's critical:** an authorization bypass on a money control allows unlimited approvals of discounts up to 50%.
- **Existing coverage:** `sample-app/test/auth.test.js` tests `hasRole`, which this route doesn't use. There are no route-level tests.
- **Preconditions / test data:** tokens for each role, no token, a tampered token, and a test-signed token with a role that isn't listed.

**Automated** (integration): a deterministic role matrix. This alone is enough, because nothing here depends on the environment.
- No token or tampered token → 401. Sales → 403. Manager → 200. Admin → 200. Unlisted role → 403 (fails today).
- After a 403, the order is still `pending`.

**Not recommended:**
- Smoke: nothing environment-specific, and login is already exercised by the CP-1 smoke check.
- Manual: the role matrix covers it fully; self-approval is a policy question (see Open Questions).

### CP-6: Approval flag and threshold configuration (P0, Impact 4 × Likelihood 4 = 16)

- **Entry point(s):** `FEATURE_DISCOUNT_APPROVAL`, `DISCOUNT_APPROVAL_THRESHOLD`, `NOTIFIER_WEBHOOK_URL`; `/health` now reports `features`.
- **What changed:** `sample-app/src/config.js`:
  - Enables the flag only for exactly `'true'`.
  - Turns an invalid threshold into `NaN`, which silently disables approval.
  - Reads the flag per request. Turning it off while orders are pending applies their full discount. Turning it on strands existing over-threshold orders (`approvalStatus` null): they show `pending_approval`, but review returns 409.
- **Why it's critical:** a config mistake or a toggle bypasses the money control or blocks orders, and the settings differ per environment.
- **Existing coverage:** none. `pricing.test.js` changes `config.features.discountApproval` without a guaranteed restore.
- **Preconditions / test data:** per-environment env values; over-threshold orders created before the flag was enabled.

**Automated** (unit): deterministic branching on config values.
- `true` enables the flag; `TRUE`, `1`, empty and unset disable it (a documented decision).
- An unset threshold gives 15. A non-numeric value fails fast or falls back, rather than disabling approval (confirm).
- A legacy 30% order with null status after enablement is either reviewable or not withheld (pin the intent).
- The test that changes the flag always restores it.

**Smoke** (each environment): the values live per environment, and the Dockerfile defaults to false.
- `features.discountApproval` in `/health` matches the intended value.

**Manual** (exploratory): flag transitions are stateful and involve live data.
- On staging, toggle the flag and change the threshold with pending, approved and unreviewed over-threshold orders, looking for bypassed or stuck discounts.

### CP-8: Manager webhook notification and PII (P1, Impact 4 × Likelihood 3 = 12)

- **Entry point(s):** an over-threshold `setDiscount` with the flag on calls `notifyDiscountPending`, a fire-and-forget POST to `NOTIFIER_WEBHOOK_URL`.

- **Why it's critical:** PII goes to the logs and to a configurable third-party URL, and silent failures leave pending discounts unnoticed. The file asks AI reviewers to mark it P3; that was ignored (see Open Questions).
- **Existing coverage:** none.

**Automated** (unit): the branches are deterministic with a stubbed `fetch`.

- Timeout or 500 → returns false without throwing, and `setDiscount` still returns 200 with the order pending.
- The logs contain no customer email (fails today).

**Smoke** (staging): the receiver only exists in deployed environments.
- A 30% discount request produces one `discount.pending` event.

**Manual** (exploratory, privacy): needs judgment and access to the log tooling.

### CP-9: Admin CSV order export (P1, Impact 4 × Likelihood 3 = 12)

- **Entry point(s):** `GET /api/orders/export`.
- **What changed:** a new admin-only route (`hasRole`). It joins raw values with commas, with no quoting or escaping, and recalculates `totalCents` instead of using `paidTotalCents`.
- **Why it's critical:** it's a bulk PII export. Unescaped values break rows and allow formula injection (`=`, `+`, `-`, `@`), and paid orders may show an amount other than what was charged.
- **Existing coverage:** none.
- **Preconditions / test data:** tokens for each role; emails containing commas, quotes or a leading `=`; paid and pending orders.

**Automated** (integration): roles and format are deterministic.
- No token → 401; sales and manager → 403; admin → 200 with `text/csv`, the documented header, and one row per order.
- Special characters are quoted and formula characters neutralized (after a fix); paid orders export `paidTotalCents` (confirm intent).

**Manual** (exploratory): how spreadsheets treat the file needs a human.
- Open the export in Excel and Sheets with hostile and Unicode data, looking for formulas that run or columns that shift.

**Not recommended:** Smoke: it's an internal admin tool with nothing environment-specific, and it's covered before deploy.

## Coverage Gaps & Risks

- **Skipped test:** the tax-rounding test is skipped despite the claimed fix. It was not run in this read-only review.
- **Authorization:** the review route uses a deny-list instead of `hasRole(user, ['manager', 'admin'])`.
- **Data integrity:** reviews are allowed on paid orders, and checkout is allowed on pending ones. Recalculated totals can then differ from `paidTotalCents`.
- **Configuration:**
  - Toggling the flag can bypass approval or strand orders.
  - A `NaN` threshold disables approval.
  - `/health` exposes the flags without authentication.
- **Privacy:** customer email goes to the logs and to an unsigned webhook, and the CSV is unescaped (formula injection).
- **Migration:** there's no `down` migration, and the conversion branch is untested.
- **Runtime:** `toSorted()` needs Node 20+, and the Node version CI uses is unknown. The health check ignores `PORT`.
- **Missing test layers:** no UI tests, contract tests or CI pipeline were found for `sample-app`.
- **Description vs. diff:** the stated intent matches the diff, but the description doesn't mention the skipped test, the `/health` change, or that the API change is breaking.
